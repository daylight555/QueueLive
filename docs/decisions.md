# Implementation decisions

1. **Spring JDBC rather than JPA.** SQL makes the exact PostgreSQL lock and partial unique indexes visible to a junior reader. The trade-off is manual mapping and more query code. Flyway owns schema changes; there is no automatic ORM schema mutation.
2. **One queue-row lock for all writes.** It is easy to audit, and gives retry lookups and ticket selection a single clear serialisation point. It limits throughput and means a slow transaction blocks other queue writes. That is acceptable for one coding lab; benchmark before considering finer-grained locks or `SKIP LOCKED`.
3. **SSE invalidation plus HTTP snapshots.** The app only needs server-to-client changes, so WebSockets would add protocol/session complexity. Snapshots simplify permissions and recovery at the cost of extra reads every ten seconds. An in-memory after-commit publisher can miss a notification on crash; polling explicitly repairs this.
4. **Database-backed sessions.** Sessions survive backend restarts alongside tickets. Cookies stay HTTP-only and auth is same-origin. This adds session rows/write traffic, and staff logout also discards a student identity in that same browser session. Use separate profiles when demonstrating both roles.
5. **Persist exact mutation results.** An idempotency retry can return an old state but cannot silently create a second assignment. Clients refresh afterwards. Stored result JSON must be considered in schema evolution and data retention.
6. **Small frontend dependency set.** React, QR generation, TypeScript and Vite; custom CSS provides the interface. No UI framework is required. This keeps the demo understandable but means accessibility and responsive behavior are our responsibility.
7. **Capacity from recent dashboard presence.** This is easy to explain and needs no extra staff availability workflow. Presence is imperfect: an unattended browser may appear available and browser timer throttling may remove a real staff member from the estimate. The UI labels estimates approximate and suppresses them when unsupported.
8. **Explicit demo provisioning.** Environment opt-in creates two accounts with a user-supplied BCrypt-hashed password; existing hashes are preserved. There are no production default credentials. A production administration flow remains future work.

Dependency versions are pinned in Maven's Spring Boot parent/BOM and npm's package-lock.json. Maven does not natively use npm-style lockfiles: the pinned BOM supplies exact transitive versions. Container tags pin releases but are not immutable digests; pin verified digests as part of a production release process.
